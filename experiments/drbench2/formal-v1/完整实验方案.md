# PaperPilot 正式配置评测方案 v1

**本次只完成第一阶段：冻结方案与配置，没有发起模型或检索调用。后续不再边跑边改。**

实验目的：先测清项目默认多 Agent 流程的真实表现，再观察关闭 fork 后的变化。评分使用公开 DeepResearch Bench II 的任务与 Rubric，以及项目现有 DeepSeek Judge；这是自定义基准评测，不是官方榜单成绩。

## 一、整个流程和固定运行顺序

| 阶段 | 固定工作 | 完成条件 | 失败时怎么办 |
|---|---|---|---|
| 1. 冻结 | 核对代码、入口、模型、工具、配置、题目、评分与失败规则 | 本方案、配置和校验清单落盘 | 不启动付费调用 |
| 2A. 执行适配离线验收 | 将公开任务接到现有生产 Runtime；测试引用导出、禁止来源、文件隔离、计量和状态记录 | 适配代码及测试哈希封存，配置差异仅限本文白名单 | 修适配，再离线检查；无在线尝试 |
| 2B. 两题默认多 Agent | 顺序运行 25-multi、12-multi，每题研究结束后逐项评分 | 两题均有可评分报告，全部 Rubric 有合法结果 | 当前阶段停止扩大；保留失败并诊断 |
| 3. 两题单 Agent | 顺序运行 25-single、12-single，预算相同，仅禁用 fork | 两组输出与评分齐全 | 保留失败，不进入十题 |
| 4. 十题配对评测 | 按下表固定顺序，逐题运行两组并评分，所有病例串行 | 每个计划病例都有产物或明确失败状态 | 不换题、不删病例；系统性适配错误则终止本轮 |
| 5. 汇总 | 输出逐题表、交付率、研究状态、Rubric 分数、耗时、Token 和失败分析 | 可追溯到原始文件和配置 | 不强行形成优劣结论 |

阶段 2/3 的进入门槛是流程和评分完整性，**不要求某个高分**。低分报告只要可评分就如实保留，不能用分数挑选进入下一阶段的题目。

阶段 4 中，个别任务自然失败也要保留并继续其他固定病例；若发现程序错误、输入污染或冻结设置被改变，则终止本轮，不继续烧预算。

## 三、使用项目本来的研究入口

冻结调用链：

```text
公开任务原始 prompt
→ open_research_runtime（本次独立数据库与空 Memory）
→ ResearchRuntime.run_auto_confirmed
→ start：生成 Brief，等待确认
→ review(confirm)：自动确认原始提案，不读取答案、不人工优化提案
→ 默认 planning
→ 同质 Research AgentGraph
→ persist_result / Vault Writer
→ 原始报告及可核查引用
→ 单独的 Rubric Judge
```

**不再使用旧 pilot 的 run_core_research 加外部 planner。** 不注入固定研究计划，不绕过报告发布，也不让聊天路由或 Quick Answer 代替深度研究。

每个病例独立建空的 managed Memory、checkpoint、黑板和派生索引，不读取个人知识库，不复用前一病例或另一组的资料。两组各自运行产品的 Brief 与规划流程，因此规划随机性属于本次端到端结果的一部分。

### 与默认配置相比，允许的适配只有这些

1. 将 Vault、checkpoint、聊天数据库、检索数据库和 archive 路径指向本次独立输出目录。
2. 原样传入公开任务及其禁止参考文章的约束；所有启用的检索路径均接受同样来源检查，包括 acquire_evidence 内部搜索/读取和 arxiv_reader。
3. 将报告内可验证的本地引用确定性导出为真实来源 URL，供外部 Judge 理解；保留原始报告，禁止改写正文、补写结论或调用额外模型润色。
4. 被动记录模型调用、耗时与返回用量，不覆盖采样参数、输出额度、超时或重试。
5. 自动确认 Brief，等价于用户确认；不增加额外研究模型或规划步骤。

禁止来源拦截仍有未知镜像等局限，需保留记录；如果确认读到了禁止资料，应标记协议违规，不拿该结果宣称有效成绩。

## 五、固定评分协议

- 官方任务、Rubric 与提示模板按哈希锁定，内容不改写。
- Judge：项目 DeepSeek，温度 0.1、top_p=1.0；与研究端分开执行，不访问个人 Memory。
- 使用完整报告，不截取“表现较好”的部分，不静默截断。单次输入超限即记录评分失败并暂停，不临时换算法。
- 每批 12 条，最多 8,192 输出 tokens。这是固定的评分设置，不是对研究 Agent 的限制。
- 继承项目 SDK 默认 timeout 与 max_retries。每个批次最多 2 次评分尝试，SDK 内部重试另记；断点恢复沿用已用尝试次数，不能重启就重置重试额度。
- 每条必须返回原始 Rubric 文本、score、reason、evidence。缺项、重复、非法分值不能算完整成功。
- 分值保留官方 1/0/-1 语义；通过率 = score=1 的条目数 / 全部条目数，0 和 -1 都在分母，另报 blocked_rate。
- 逐题维度分、逐题总分均保留。跨题主指标为固定病例上的逐题总分均值，微平均另列；必须同时写出评分完成数和计划数。
- 无报告或评分失败留空，不直接记零分，也不悄悄删除。只有完成全部计划评分，才给该阶段完整均值；否则称“已评分子集均值”，不用于排序结论。

本协议不是官方 Gemini Judge 配置，因此不与官方榜单直接比较，也不把通过率叫作事实准确率。

## 六、报告与失败判定

分别记录四层状态，禁止合成一个 success：

1. 执行是否结束；
2. 报告是否为真正正文；
3. 研究是否充分或因何结束；
4. Rubric 是否完整评分。

报告为空、纯错误信息、纯工具协议文本或确定性 fallback 时，记交付失败；核心标为 valid 也不能越过独立检查。**不再以 500 字符这类临时长度门槛替代正文判断。**
partial 但形成可评分报告时照常评分，保留停止原因。引用问题单独列出；不能通过删除正文、补造引用来提高成绩。

每个病例只安排一次研究轨迹。网络重试按已冻结的 SDK/研究内部规则执行，病例失败不自动新建多次轨迹取最好成绩。

如果必须修改代码、入口或配置：终止当前实验，保存原始结果，建立 v2 方案与新版本；重新运行两题两组以及受影响的正式病例。不能只重跑低分项并替换原分数。

## 七、运行与计费记录

每组、每题串行，研究结束后先评分，再进入下一例；避免同账户并发调用干扰此次测量。每例保存时间戳、版本、配置、全部调用用量、失败请求、报告和逐条评分。
API 返回 Token 是已知用量；没有返回用量的超时请求记未知。研究、评分、工具费用分别记录，没有计费数据就不捏造金额。
前两题完成后给出实测成本范围，再决定后续阶段的调用批次；不能因为成本高就偷偷降低本轮研究预算。
